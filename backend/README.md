# Backend YourMettings

Python 3.11+, PostgreSQL, локальный Ollama и GigaAM v3 (отдельное ASR-окружение). Команды ниже выполняются из `backend/` в PowerShell.

## Обычный запуск на Windows

Дважды нажмите ярлык **«YourMettings — запуск сервера»** на рабочем столе. Он открывает PowerShell, проверяет PostgreSQL с конфигурацией приложения, Ollama и выбранную модель, постоянный ASR-worker с GigaAM/VAD, затем запускает один backend либо использует уже работающий. Окно остаётся открытым, включая ошибки. В обычном настроенном окружении права администратора не нужны. Закрытие окна не останавливает серверы.

Из PowerShell в корне репозитория:

```powershell
.\start-dev.ps1
# Только диагностика: не запускает службы/процессы и не загружает модель.
.\start-dev.ps1 -CheckOnly
# Если на ПК несколько служб PostgreSQL, явно выберите существующую.
.\start-dev.ps1 -PostgresService postgresql-x64-18
```

Признак готовности — итоговая строка **«ГОТОВО: PostgreSQL, Ollama, ASR (если включён) и backend проверены»**. Перед ней выполняются реальный SELECT и сверка миграций, проверка API Ollama, тега OLLAMA_MODEL и загрузки модели (при обычном запуске), heartbeat ASR с загруженными GigaAM/VAD, `/health`, OpenAPI и чтение папок через backend. Холодная загрузка Qwen и ASR может занять несколько минут. CheckOnly не загружает Qwen, но требует готового ASR-worker, если ASR_ENABLED=true.

Используются существующее `backend/.venv` и настройки `backend/.env` с обычным приоритетом переменных окружения приложения. Скрипт не устанавливает зависимости, не создаёт БД, не запускает миграции, не скачивает модели и не меняет данные диагностическими запросами. При старте самого backend остаются его прежние правила инициализации/восстановления обработки. Повторный и одновременный запуск не создают дубли. Состояние последней проверки: `%LOCALAPPDATA%\YourMettings\logs\last-start.json`; логи новых процессов: та же папка. Пароли и `.env` не выводятся.

LAN по умолчанию: `192.168.1.100:8000`, loopback: `127.0.0.1:8000`. Если адрес ПК изменился, используйте `.\start-dev.ps1 -LanHost <IPv4 ПК>` и укажите тот же адрес Flutter-клиенту. Скрипт проверяет наличие интерфейса и listener; доступ с телефона зависит также от Wi-Fi/VPN. Firewall, VPN, маршрутизация, ExecutionPolicy и другие системные настройки не меняются.

Типичные ошибки:

- **PostgreSQL:** существующая остановленная служба запускается, если Windows разрешает это. При отказе прав запустите её через `services.msc` с необходимыми правами и повторите обычный запуск. Если служба уже работает, проверьте адрес/порт, имя БД и credentials локально в `.env`; рабочая служба не перезапускается. Несколько служб требуют параметра PostgresService.
- **Схема БД:** проверьте `alembic upgrade head` по инструкции ниже; миграции автоматически не выполняются.
- **Ollama:** проверьте OLLAMA_BASE_URL и `ollama list`. Если тег отсутствует, скрипт сообщает ошибку и ничего не скачивает. Ошибка загрузки установленной модели требует проверки свободной RAM/VRAM и лога Ollama.
- **GigaAM:** проверьте ASR_HOME, отдельную .venv, локальные models, FFmpeg и HF-кэш/VAD. asr_environment_missing/asr_model_missing означают неполное окружение; asr_load_failed — в том числе отсутствующий/недоступный кэш VAD; asr_cuda_unavailable — CUDA недоступна; asr_gpu_memory — нехватка VRAM. Рабочий runtime ничего не скачивает. Запустите повторно launcher после устранения причины; незавершённые ASR-задания сохраняются в PostgreSQL.
- **Порт 8000:** посторонний/неопознанный процесс не завершается. Проверьте его владельца; скрипт откажется запускать второй экземпляр. Неисправный собственный backend также не дублируется.
- **Изменён `.env`:** после завершения обработок остановите собственный backend и запустите снова, чтобы применить настройки. Уже работающий процесс не перезапускается автоматически.
- **PowerShell запрещает запуск скрипта:** проверьте применённую локальную политику с администратором. Ярлык не обходит её и не изменяет настройки безопасности.

Чтобы остановить **только backend**, дождитесь завершения генераций, запустите CheckOnly и используйте актуальный PID из строки `PID backend`. В PowerShell выполните `Stop-Process -Id <этот PID>`. Не завершайте произвольный процесс только по номеру порта. PostgreSQL и Ollama при этом остаются работающими. Повторное нажатие ярлыка снова поднимет backend.

Ярлык — локальный `.lnk`, в Git не хранится. Его цель: Windows PowerShell с аргументами `-NoLogo -NoProfile -NoExit -File "<репозиторий>\start-dev.ps1"`, рабочая папка — корень репозитория; значок берётся из Windows shell32.dll.

## Первичная настройка вручную

```powershell
python -m venv .venv
& .\.venv\Scripts\python.exe -m pip install -e '.[test]'
Copy-Item .env.example .env
# Заполните DATABASE_URL, TEST_DATABASE_URL и OLLAMA_MODEL локально.
& .\.venv\Scripts\python.exe -m alembic upgrade head
& .\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
& .\.venv\Scripts\python.exe -m pytest
```

Swagger: http://127.0.0.1:8000/docs. OpenAPI: http://127.0.0.1:8000/openapi.json.

Для телефона используйте LAN-IP ПК и запуск с `--host <LAN-IP-ПК>`. При необходимости разрешите входящий TCP 8000 только для частной сети и локальной подсети в Windows Firewall. Не настраивайте проброс порта роутера.

Для одновременного доступа с ПК и телефона одним процессом:

```powershell
& .\.venv\Scripts\python.exe -m app.run --lan-host 192.168.1.100 --port 8000
```

Это слушает только loopback и выбранный LAN-IP, не VPN-интерфейсы. Подставьте актуальный IPv4 ПК. Если Windows блокирует подключение телефона, предусмотрен `scripts/allow_lan.ps1`: запустите его явно из Administrator PowerShell с актуальными `-LanAddress` и `-RemoteSubnet`. Он добавляет только правило входящего TCP для заданных адреса, подсети и порта, действует при любом профиле Windows и не отключает Firewall. Удалить созданное правило: `Remove-NetFirewallRule -Name YourMettingsBackendLAN`. В этой сессии правило автоматически не добавлялось.

Авторизация пока отсутствует: все клиенты работают с одним серверным тестовым пользователем. Используйте только доверенную локальную сеть. Мобильный клиент не получает credentials PostgreSQL или адрес Ollama.

Настройка `.env` читается независимо от текущей папки; секреты не коммитятся. Реальный тег проверьте через `ollama list`; новую модель backend самостоятельно не скачивает.

## PostgreSQL

Создайте отдельную роль приложения с LOGIN и две базы, принадлежащие ей: `yourmettings` и `yourmettings_test`. Не используйте роль postgres для обычной работы backend. Connection strings укажите в локальном `.env` (пример в `.env.example`). Миграции запускаются вручную до старта; приложение не создаёт таблицы самостоятельно. При старте идемпотентно создаётся фиксированный пользователь с отключённым входом.

Интеграционные тесты используют только PostgreSQL из TEST_DATABASE_URL и очищают таблицы этой базы. Имя тестовой базы должно оканчиваться на `_test` и отличаться от базы разработки. Если TEST_DATABASE_URL отсутствует, интеграционные тесты пропускаются; это не подтверждает готовность backend.

## Обработка и тесты

Один процесс Uvicorn, без `--workers` и без `--reload` во время генерации. Фоновая задача не держит транзакцию при вызове модели. После перезапуска незавершённые обработки становятся error и допускают явный повтор.

Текст блокируется во время генерации, разблокируется при ошибке до первого успеха и навсегда блокируется после первого успешного сохранения summary. При удалении последнего summary неиспользуемый transcript удаляется атомарно; общие источники, активные обработки и внешние FK-зависимости сохраняются. Для сохранённого источника постоянная блокировка не снимается.

```powershell
& .\.venv\Scripts\python.exe -m pytest -q
& .\.venv\Scripts\python.exe -m alembic check
# После запуска backend: реальная генерация (явная операция, не часть обычного pytest).
& .\.venv\Scripts\python.exe tests/e2e_real.py 'http://<LAN-IP-ПК>:8000'
```

E2E создаёт только свои диагностические папки и короткий transcript в dev-БД, проверяет реальную генерацию с настройками, отсутствие Markdown-таблиц, редактирование, удаление дерева и очистку ненужного transcript. В конце удаляет созданные этим запуском данные. При сбое диагностические записи могут остаться для проверки; существующие пользовательские записи не очищаются массово.

`requirements.lock` фиксирует проверенные версии окружения. Для воспроизведения: `python -m pip install -r requirements.lock`, затем `python -m pip install -e . --no-deps`. Конфигурация Ollama host может отличаться от стандартного порта 11434; проверяйте OLLAMA_HOST и локальную настройку сервера.

Контракт Flutter: `../docs/API_CONTRACT.md`. Статусы и ошибки фоновой генерации читаются через polling.

Настройки операции: detail_level = brief/normal/detailed (по умолчанию normal), focus_areas = список акцентов (по умолчанию []), additional_instructions = пожелания до 2000 символов (по умолчанию ""). Настройки передаются обоим endpoints запуска, хранятся в processing_options и входят в Idempotency-Key. Они не меняют размер контекста модели. Дополнительный текст передаётся как пользовательские данные отдельно от системных правил; у модели нет инструментов или доступа к БД и секретам.

Удаление папки: `DELETE /api/v1/folders/{id}?mode=with_contents&confirm=true`, после подтверждения в Flutter. Удаляется дерево и summary, оставшиеся без папок; summary в других папках сохраняются. Режима переноса в корень нет. Во время генерации в папке возвращается 409 folder_processing; повторите после её завершения. Все изменения и очистка transcript входят в одну транзакцию PostgreSQL.

Основной сценарий Flutter: `POST /api/v1/transcripts/process` с `text`, `title`, `folder_ids` и стабильным `Idempotency-Key`. Ответ 202 содержит transcript_id для polling. Повтор исходного запроса возвращает текущее состояние без новой генерации; явный повтор после ошибки выполняется через `POST /api/v1/transcripts/{id}/process`.

Длинные транскрипты и нагрузка на GPU требуют отдельной проверки: ограничение символов API не гарантирует, что весь текст поместится в контекст выбранной модели. В первой версии используется контекст, настроенный в Ollama; автоматического разбиения текста пока нет.

## Запись аудио и постоянный GigaAM-worker

Перед запуском обновлённой версии примените **аддитивную миграцию 0004**: `.\.venv\Scripts\python.exe -m alembic upgrade head`. Она добавляет audio_sessions/audio_chunks/asr_worker_state, не удаляя прежние summary и transcripts. Существующие текстовые API продолжают работать.

Ресурсы ML отделены от backend. ASR_HOME по умолчанию `<репозиторий>/asr`; в локальном backend/.env можно указать существующую ASR-папку другого worktree. В ней нужны `.venv/Scripts/python.exe`, `models/v3_e2e_rnnt.ckpt`, `models/v3_e2e_rnnt_tokenizer.model`, `tools/ffmpeg-shared/bin/ffmpeg.exe` и `.cache/huggingface` с уже подготовленным VAD. Код serve.py берётся из **текущего backend-репозитория**, ресурсы — из ASR_HOME. Относительный ASCII-путь models сохраняет совместимость SentencePiece на Windows с кириллицей в профиле.

Для новой установки используйте проверенные ASR-инструкции [ASR_RESEARCH.md](../docs/ASR_RESEARCH.md), `asr/setup-longform.ps1` и lock-файл зависимостей в ASR-папке. Доступ к pyannote требует принятых условий и локального HF_TOKEN (из окружения или Windows user variable); токен не передаётся Flutter и не выводится. Runtime работает с offline-кэшем, без загрузки других моделей. Зависимости torch/gigaam не устанавливаются в backend/.venv. Существующее рабочее ASR-окружение можно переиспользовать через ASR_HOME.

Штатный запуск — корневой start-dev.ps1/ярлык. Ручной запуск из backend, без активации ASR-venv:

```powershell
.\.venv\Scripts\python.exe scripts/asr_worker.py
```

Координатор в backend-venv владеет PostgreSQL-очередью и запускает один постоянный ML-процесс в ASR-venv. GigaAM v3_e2e_rnnt и VAD загружаются один раз на CUDA, затем переиспользуются. Готовность означает успешную загрузку обоих компонентов, не просто наличие PID. Windows mutex + advisory lock исключают дубли; штатный повторный запуск переиспользует worker. В логах launcher видны путь к ASR-логу, готовность, времена/VRAM заданий и безопасные коды ошибок; исходные тексты и секреты в эти сообщения не включаются. Сторонние библиотеки могут выводить технические предупреждения в тот же локальный лог.

Приём файла: временная загрузка → реальная проверка FFmpeg → **байты BYTEA + метаданные + queued одним commit** → HTTP-подтверждение. Это даёт атомарность без распределённой транзакции PostgreSQL/файловой системы. Worker берёт короткую блокировку задания, закрывает транзакцию, распознаёт, затем отдельным commit сохраняет текст/таймкоды и убирает payload. При ошибке payload остаётся. После распознавания исходное аудио не архивируется. Учитывайте объём PostgreSQL/WAL/backup при длинных записях.

Временные копии worker лежат в игнорируемой Git папке backend/.runtime/asr, удаляются после работы; после аварии их очищает следующий worker под singleton-блокировкой. Это не единственные экземпляры ожидающих аудиобайтов — они остаются в PostgreSQL. Прерванные HTTP-загрузки не подтверждаются, не создают очередь; временная проверка очищается при нормальном выходе. После принудительного завершения FastAPI могут остаться не подтверждённые вспомогательные каталоги yourmettings-validate-* в пользовательском TEMP; они не участвуют в восстановлении и могут быть удалены после остановки backend/FFmpeg. Принятые queued/failed аудиозадания по таймеру не удаляются.

Сбой FastAPI не прерывает независимый ASR. При аварии worker следующий запуск возвращает transcribing в queued; generation/attempt исключают сохранение устаревшего результата. Дочерний ML-процесс следит за жизнью координатора и выходит при его гибели. При сбое PostgreSQL/таймауте worker прекращает работу, сохраняя задания; после устранения причины снова запустите start-dev.ps1. Автоперезапуск Windows-службой здесь не настроен. Не запускайте несколько FastAPI workers и несколько ASR-worker.

ASR_GPU_SERIAL=true (по умолчанию) ограничивает GPU-операции GigaAM и Qwen общим session advisory lock. Транзакции во время вычислений закрыты. Модели остаются в памяти: последовательность не заменяет проверку вместимости VRAM. Ollama и чужие GPU-процессы автоматически не выгружаются/не завершаются. ASR_ENABLED=false отключает запуск и требование готовности ASR в launcher для режима только текстового backend; API и сохранённая очередь остаются доступны, работающий worker эта настройка сама не останавливает.

Настройки и значения по умолчанию перечислены в .env.example. Базовый фрагмент 300 секунд, максимум 360 секунд и 32 МиБ, до 240 частей, перекрытие до 3000 мс, проверка файла до 30 с, загрузка ASR до 180 с, задание до 600 с. Корректируйте лимиты согласованно; Flutter получает их в AudioSessionOut.

Flutter-сценарий: POST /audio-sessions → независимые M4A/AAC-файлы POST .../chunks с последовательными номерами → POST .../complete с общим количеством → polling → просмотр/правка единого transcript → POST .../confirm → прежний polling Qwen/summary. До confirm Qwen не вызывается. Правила границ, идемпотентности и все JSON-структуры: [API_CONTRACT.md](../docs/API_CONTRACT.md). Предпочтительны непрерывные файлы с границей на паузе; перекрытия требуют осторожной проверки текста, без обещаний идеальной точности ASR.

Чтобы остановить worker, дождитесь окончания своих задач. Найдите PID координатора из asr_worker_state (или командной строки процесса scripts/asr_worker.py), проверьте принадлежность этому репозиторию и остановите **только этот PID** через Stop-Process. Его ML-процесс завершится автоматически. Не останавливайте Ollama/PostgreSQL и не выбирайте произвольный python.exe. При следующем запуске очередь восстановится.

## Проверка аудиосценария

Удаление черновика после ASR: `DELETE /api/v1/audio-sessions/{id}?confirm=true`, только ready_for_review до первого подтверждения Qwen. Успех и повтор — пустой 204; неизвестный/чужой ID — 404; отсутствие подтверждения — 422; неподдерживаемое состояние, активная загрузка, зависимости или невозможность безопасной очистки — 409. Создавайте аудиосессии со стабильным Idempotency-Key: после явного DELETE повтор исходного POST вернёт 410 audio_session_deleted, не создавая встречу заново. Завершённые встречи удаляются прежним путём через summary. Точный контракт и гарантия очистки: [API_CONTRACT.md](../docs/API_CONTRACT.md).

Перед использованием нового DELETE примените **миграцию 0005**: `.\.venv\Scripts\python.exe -m alembic upgrade head`. Она добавляет только audio_session_deletions с минимальными квитанциями, без изменения/удаления существующих встреч. Квитанции не содержат аудио или текста, сохраняют UUID/владельца/ключ/hash/время и не очищаются автоматически. Нужен плановый перезапуск backend **и ASR-worker** после завершения текущих задач: новые рабочие копии ASR именуются job-{session_id}-*, вложенный decoder-temp очищается до публикации результата. Модели, алгоритм ASR и очередь не меняются. Сам launcher использует уже запущенные процессы; он не применяет миграции и не перезапускает их автоматически. Не останавливайте службы PostgreSQL/Ollama или чужие python-процессы.

DELETE не требует выгрузки GigaAM и не удаляет общий worker-state. Все authoritative-данные и квитанция меняются одним commit; временные файлы — только ненужные рабочие копии готовых частей, очищаются до него. При ошибке очистки/commit записи БД сохраняются. Shared advisory-lock upload держит одно соединение без открытой транзакции на время запроса; DELETE при занятом upload возвращает 409 вместо частичного удаления. Сохранение/продолжение нескольких локальных черновиков остаётся задачей Flutter, серверного CRUD черновиков нет.

Обычный pytest проверяет API и реальные транзакции выделенной тестовой PostgreSQL; ASR-результаты и Qwen в этих тестах управляемые. FFmpeg проверяет настоящие WAV-байты. Покрыты дубли/конкурентные загрузки, ошибки и прерванные файлы, лимиты, порядок/пропуски, complete во время работы, retry, восстановление/устаревшие результаты, перекрытия, просмотр/правка и ровно один запуск Qwen. Прежние тесты проверяют сохранность/удаление существующих данных и сценарии launcher.

Реальный E2E — отдельная явная команда, требует запущенных backend/ASR/Ollama:

```powershell
.\.venv\Scripts\python.exe tests/e2e_audio_real.py --audio 'C:\path\to\recording.mp3' --chunk-seconds 300
```

Он создаёт два M4A/AAC-фрагмента, загружает их в обратном порядке с повтором, ждёт GigaAM, проверяет PostgreSQL и отсутствие Qwen до подтверждения, подтверждает текст, получает реальный summary, проверяет один LLM-attempt и удаляет только свою диагностическую встречу. При сбое свои диагностические записи остаются для расследования; массовой очистки нет. Входное аудио не изменяется. Результат проверенного запуска — [ASR_E2E_RESULT.json](../docs/ASR_E2E_RESULT.json): 600,064 с аудиокниги, ASR с передачей 23,781 с, полный путь 37,875 с, пиковое выделение ASR около 863 МиБ. Это не гарантия для совещаний/нагруженной GPU; качество на телефоне не проверялось, Flutter ещё не подключён.

Отдельно проверено принудительное завершение только созданного для проверки координатора во время обработки собственного 300-секундного задания: после штатного запуска новый worker восстановил payload из PostgreSQL, распознал его со второй попытки и собрал transcript; Qwen без подтверждения не запускался. Повтор start-dev.ps1 и CheckOnly сохранил PID backend и ASR без дублей. Проверка HTTP loopback успешна; дополнительный запрос с ПК к LAN-IP в этой сессии завершился таймаутом при сохранённом LAN-listener. Настройки сети/Firewall/VPN не изменялись.


## Шаблоны обработки

Каталог: `GET /api/v1/summary-templates`. Семь системных шаблонов доступны только для чтения; копирование создаёт редактируемый пользовательский вариант. Конструктор хранит JSONB с упорядоченными ordinary/repeated разделами, максимум два уровня. Полный контракт CRUD, UUID, JSON и ограничения: [API_CONTRACT.md](../docs/API_CONTRACT.md#шаблоны-генерации-контракт-flutter).

В существующие запросы обработки текста и confirm аудиосессии добавлено необязательное `template_id`. Без выбора действует «Универсальное совещание». При принятии сохраняется полный снимок; изменение или удаление шаблона не меняет созданные summary. Существующие detail_level/focus_areas/additional_instructions сохранены.

`POST /api/v1/template-previews` с text и текущим inline template возвращает 202; результат получают polling `GET /api/v1/template-previews/{id}`. Это временный тест в памяти, без сохранения встречи или исходного текста в БД; после перезапуска повторите POST. Вход до12000 символов, TTL15минут, максимум2активных теста. Работает в существующем одном backend-процессе, без дополнительных служб.

Для обновления БД перед запуском новой версии, из backend:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Миграции 0006/0007 добавляют каталог с фиксированными системными UUID и nullable snapshot в summaries; прежние данные сохраняются. После миграции требуется обычный перезапуск backend, ASR-worker менять не требуется. Не запускайте два экземпляра backend. Автоматический seed не выполняет миграции.

Проверки на отдельной тестовой PostgreSQL:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Реальная проверка установленной модели Ollama (два синтетических транскрипта, включая длинный; обычные записи приложения не создаёт):

```powershell
.\.venv\Scripts\python.exe tests/e2e_templates_real.py
```

Примеры и результаты сохраняются в `docs/examples/template_*`. Параметры модели temperature/контекста не меняются произвольно. Сервер задаёт приоритетные правила достоверности и проверяет структуру JSON-ответа перед сборкой Markdown; фактическое содержание ответа всё равно требует пользовательской проверки. Навигация summary содержит heading_index/line_index и ASCII ID, Flutter обрабатывает переходы сам, без зависимости от GitHub-якорей.
