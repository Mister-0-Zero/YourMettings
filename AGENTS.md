# Отчётность по работе над YourMettings

По прямому указанию Алексея от 31 октября 2026 года после каждого завершённого задания или существенного этапа сохранять отчёт в `docs/` репозитория и публиковать его на GitHub в рабочей ветке. Это относится также к диагностике, если по её результатам код не менялся, и к этапам с незавершёнными проверками: их ограничения нужно указать явно.

- Использовать Markdown. Для мобильной разработки: `docs/MOBILE_<тема>_<YYYY-MM-DD>.md`. Для продолжения того же этапа обновлять его отчёт, не создавать дубликаты. Если `docs/` отсутствует — создать.
- Описывать результат для пользователя, причины исправленных ошибок, существенные изменения, фактически выполненные проверки и их результаты, ограничения, нерешённые вопросы и следующий необходимый шаг. Указывать коммиты реализации; при выдаче APK — версию, расположение, SHA256 и сведения о проверке подписи/установки, если они проверялись.
- Отделять собственные проверки от сведений пользователя и других агентов, автоматические тесты — от реального устройства, исторические результаты — от текущих. Не объявлять сборку, установку, исправление или интеграцию успешными без соответствующей проверки.
- Не публиковать ключи доступа, токены, пароли, приватные файлы, содержимое пользовательских встреч и сырые логи с такими данными. Использовать минимальные обезличенные сведения.
- Добавлять ссылку на новый/обновлённый отчёт в `docs/MOBILE_REPORTS.md` для мобильных задач. Сводный отчёт на 31.10.2026: `docs/MOBILE_PROGRESS_REPORT_2026-10-31.md`.
- Перед публикацией проверить ссылки и соответствие отчёта изменениям. Делать commit и push в согласованную рабочую ветку; не выполнять merge или force-push ради публикации. Если push не удался, сохранить отчёт локально и явно сообщить, что GitHub ещё не обновлён.
- В итоговом сообщении кратко сообщать результат, проверки, коммит и ссылку на отчёт GitHub. Это правило само по себе не требует дополнительных тестов приложения для чисто документальных правок.
