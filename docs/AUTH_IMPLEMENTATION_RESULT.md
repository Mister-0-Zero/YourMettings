# Результат: email OTP и изоляция пользователей

27 октября 2026. Код/API: **6d0bae3**, ветка backend. Flutter, mobile-worktree, main, VPS/DNS/Firewall/VPN не изменялись.

## Что реализовано

- Публичные POST /api/v1/auth/request-code, /verify-code, /refresh; защищённые POST /auth/logout и GET /auth/me. Все прочие пользовательские API и HTTP OpenAPI/Swagger/ReDoc требуют Bearer. Health по-прежнему отдаёт только status=ok.
- Разбор/нормализация email корректным парсером; точный cbr.ru либо явно разрешённый административный адрес из приватного .env. Admin имеет только свои данные и те же операции, что обычный пользователь.
- Шесть цифр OTP, 10 минут, HMAC-SHA256, пять попыток, однократность, атомарность при конкурентной проверке. Лимиты повторной отправки/email/IP в PostgreSQL, без логирования кода. SMTP только TLS, без публичного mock/универсального кода.
- Opaque access token до 15 минут, серверные хеши, проверка отзыва на каждом запросе. Remembered refresh-семья до 30 дней; memory-only session_token до 24 часов с обновлением во время живого процесса Flutter. Абсолютный срок не продлевается. Только Flutter может гарантировать отсутствие записи memory-only токенов на диск.
- Ротация с обязательным Idempotency-Key и окном восстановления 120 секунд: те же token+key возвращают прежнюю пару; иной повтор использованного токена отзывает семью. В БД нет plaintext renewal-квитанций. access_expires_at позволяет не продлевать срок ошибочно при потерянном ответе.
- Logout отзывает текущую серверную семью, включая выход с уже истёкшим access; локальный сброс не считается подтверждённым выходом. Другие устройства не отзываются автоматически.
- Проверенный user UUID переносится через все API, дополнительные upload DB sessions, Qwen callbacks и maintenance. ASR берёт владельца из сохранённой сессии; поздние результаты не меняют чужого владельца. Глобальные проверки ссылок сохраняют общие источники, владение summary не открывает чужой сырой текст.
- JSON cap2 MiB до JSON-буферизации, streaming upload cap32 MiB, tenant quota активных Qwen/audio/payload. Proxy trust пуст по умолчанию, только явно заданные IP/CIDR, без wildcard или /0. Все изменения не публикуют инфраструктуру в интернет.

Новых серверных CRUD черновиков/настроек нет: незавершённые Transcript/AudioSession и существующие параметры изолированы владельцем; локальные черновики/настройки должен разделять Flutter по user.id.

## Проверки

Полный PostgreSQL прогон: **337 passed**, 63,14 с; одно прежнее Starlette/httpx deprecation warning. Новые проверки включают OTP/домен/admin, TTL/однократность/лимиты, remember true/false, конкурентный refresh/потерянный ответ/reuse, logout с истёкшим access, два реальных авторизованных пользователя, admin IDOR, папки/исходники/summary/templates/preview/variants, upload после refresh без дублирования, Qwen callback ownership и restart ASR обоих владельцев без HTTP identity.

Тест populated0008→0009 проверяет UUID/тексты/связи, отдельные проверки — подтверждённую legacy-привязку и запрет захвата первым корпоративным пользователем. Прежние регрессии Qwen/GigaAM/аудио/удаления включены. Mail и inference в автоматических тестах заменяются только dependency seams; это не подтверждение повторного запуска реального инференса. Реальные модель/VAD проверены launcher по готовности ресурсов; новые веса/контекст/GPU-параметры не менялись.

Проверка работающего HTTP: /health200; папки/summary/шаблоны/примеры/auth-me/docs/OpenAPI без Bearer401; намеренно неизвестный Bearer достигает DB lookup и даёт401 invalid_access_token; запрещённый email403; oversized JSON413. Не создавались фиктивные подтверждённые production-пользователи или сессии для обхода почты. Экспорт OpenAPI совпадает с app.openapi(), все приватные операции объявляют HTTPBearer.

## Рабочая база и запуск

Перед0009 созданы два приватных pre-auth pg_dump custom-архива вне репозитория, проверены pg_restore --list и SHA-256. Последний архив — pre-auth-20261027-102600.dump. После применения миграции сверены хеши старых колонок всех бизнес-таблиц: UUID, содержимое и связи не изменились; изменчивый heartbeat worker не сравнивался. Alembic check: No new upgrade operations detected.

Старые записи не перемещались между UUID. Legacy-аккаунт зарезервирован; AUTH_LEGACY_ADMIN_EMAIL и allowlist настроены приватно на указанный владельцем адрес. Привязка ещё требует настоящего verify-code владельцем — она не выполнена административной SQL-подменой.

Новый backend запущен из существующего окружения через start-dev.ps1, один процесс на прежних loopback/LAN адресах. PostgreSQL, Ollama/Qwen, ASR с GigaAM/VAD готовы. Повтор CheckOnly проходит. Backend обновлялся только при отсутствии авторизованных сессий/незавершённого аудио; чужие процессы/службы не останавливались. Старый Flutter без auth теперь получает401 и должен быть обновлён.

## SMTP: внешняя блокировка

Приватные настройки отправителя подготовлены; .env игнорируется Git, секрет/личные адреса не включены в исходники, схему или журналы. SMTP password прочитан именно из нужного backend/.env; нет дублированных переменных, перекрытия окружением или пробелов.

Установлено защищённое SSL-соединение с Яндексом465, но SMTP AUTH отклонён **535**, в том числе после сообщения владельца о новом пароле приложения. Проверены короткий логин и полный адрес; реальный POST /auth/request-code завершился **503 email_delivery_unavailable**. Успех отправки не имитировался, письма с кодом не отправлены. Владелец уточнил домен отправителя yandex.com; приватные SMTP_USERNAME/SMTP_FROM_EMAIL исправлены. После смены домена535 сохраняется; безопасный текст ответа сервера — «This user does not have access rights to this service».

[Официальная справка Яндекс ID](https://www.yandex.ru/support/id/ru/authorization/app-passwords) указывает **2–3 часа до начала действия нового пароля приложения**. Проверки выполнялись раньше этого срока; задержка активации — вероятное объяснение, не подтверждённая единственная причина отказа. Последний пароль сохранён, дальнейшее пересоздание/перебор прекращены. После периода активации повторить SMTP AUTH и настоящую отправку на разрешённый адрес; до успеха почта остаётся непроверенной. Доставка в cbr.ru не проверена — требуется реальный корпоративный адрес и проверка принимающего сервера. До этого и настройки HTTPS-шлюза система не объявляется готовой к публичной эксплуатации.
