# Авторизация: настройка и сохранение прежних данных

Миграция `0009_email_auth` добавляет OTP challenges, серверные сессии и хеши токенов. В users появляются role, email_verified_at и legacy_claim_pending. UUID, исходные тексты, встречи, папки, шаблоны, технические кандидаты и аудиоданные не переносятся в новые строки и не удаляются.

## Безопасная последовательность

1. Дождаться завершения активной обработки. Не открывать HTTP в интернет. Сделать приватную PostgreSQL-резервную копию `pg_dump --format=custom --no-owner --no-acl` и проверить `pg_restore --list`. Не передавать пароль в командной строке; использовать локальный секрет/PGPASSWORD только в окружении дочернего процесса. Архив содержит пользовательские данные — не помещать в Git/общую папку.
2. Проверить, что работаем в отдельном корневом репозитории YourMettings и ветке backend. Обновить backend зависимости: `.venv\Scripts\python.exe -m pip install -e ".[test]"` из backend.
3. В приватном backend/.env задать AUTH_SECRET (случайный секрет минимум 32 байта), AUTH_ADMIN_EMAILS (JSON список точных адресов), AUTH_LEGACY_ADMIN_EMAIL (ровно один адрес будущего владельца, входящий в allowlist) и SMTP. `.env.example` не содержит конкретных персональных адресов/секретов.
4. Выполнить `.venv\Scripts\python.exe -m alembic upgrade head` и `... -m alembic check`. Проверить UUID/связи/данные относительно backup до запуска нового процесса. Для 0009 меняется только резервирование прежнего пользователя; массового изменения owner_user_id нет.
5. Перезапустить один backend после завершения текущих обработок. ASR-ресурсы, модель, постоянный worker, Firewall и VPN не меняются. Старый Flutter без Bearer после активации получит 401: согласовать выпуск интерфейса входа. Не возвращать общий test-user fallback ради совместимости.
6. Запросить код **для настроенного административного адреса**, подтвердить его штатным verify-code. После подтверждения в той же транзакции прежний UUID `00000000-0000-0000-0000-000000000001` получает этот email, role=admin, email_verified_at и legacy_claim_pending=false. Проверить собственную историю через авторизованный API.

Первый корпоративный вход всегда создаёт отдельного пользователя. Пока владелец не подтвердил свой код, прежняя запись зарезервирована и недоступна через новую авторизацию. Секретные тестовые коды, fallback-аккаунты и настройка обхода auth отсутствуют. На новой пустой БД общий пользователь вообще не создаётся. Только system templates остаются общими для чтения.

Если административный email уже успел создать отдельного пользователя до корректной настройки legacy привязки, сервер возвращает 409 legacy_claim_conflict. Он не объединяет аккаунты и не передаёт записи автоматически. Исправление требует отдельной проверки оператором с backup. Не меняйте legacy адрес после успешной привязки в расчёте повторно присвоить старые данные.

## Почта

Настройки: SMTP_HOST, SMTP_PORT, SMTP_SECURITY=ssl/starttls, SMTP_USERNAME, SMTP_PASSWORD, SMTP_FROM_EMAIL. При заданном username нужен password; без полной настройки/при SMTP-ошибке код не выдаётся API как успешно отправленный. Отправитель и разрешённый административный адрес — разные роли: SMTP_FROM_EMAIL не становится автоматически пользователем/admin.

Для Яндекс Почты используйте отдельный **пароль приложения «Почта»**, не основной пароль аккаунта. По [официальной инструкции](https://www.yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others): smtp.yandex.ru, SSL 465 или STARTTLS 587; доступ почтовых клиентов/паролей приложений включается в настройках ящика. Пароль сохраняется локально только в backend/.env, никогда в чат, Flutter, Git или логи.

SMTP 202 означает, что сервер исходящей почты принял письмо, а не подтверждённую доставку адресату. Доставка на конкретный cbr.ru пока требует проверки реальным владельцем корпоративного ящика; вход на внешний admin email этого не доказывает. Mock адаптер доступен только через Python dependency override в тестах, публичного режима «показать код» нет.

AUTH_SECRET храните стабильно и резервируйте приватно: он нужен для HMAC кодов и идемпотентных повторов refresh. Его замена требует отдельной операции отзыва сессий/кодов; простая замена ключа во время живых refresh-квитанций нарушает восстановление потерянного ответа. Не регенерируйте его при каждом запуске.

## Запуск и диагностика

Ярлык/start-dev.ps1 остаётся прежним. Launcher проверяет PostgreSQL/схему, Ollama, ASR и /health. Вместо чтения чужой истории без авторизации он посылает намеренно неизвестный Bearer в /auth/me: ожидаемый 401 invalid_access_token подтверждает, что backend действительно прочитал таблицу токенов в PostgreSQL. Это не тестовая сессия и не обход прав. Неавторизованный /folders и OpenAPI должны давать 401, старый незащищённый сервер проверку не пройдёт.

Отдельное предупреждение запуска показывает отсутствие AUTH_SECRET/SMTP; готовые процессы не означают готовую доставку писем. Логи не содержат адресов, кодов или реквизитов. При изменении .env уже работающий сервер нужно штатно перезапустить: launcher не останавливает чужие/активные процессы и не создаёт дубликат.

HTTP OpenAPI/Swagger/ReDoc теперь требуют Bearer. Для разработки контракта без входа можно получить схему локально: из backend запустить `python -c "import json; from app.main import app; print(json.dumps(app.openapi(),ensure_ascii=False,indent=2))"`. В репозитории [openapi.json](openapi.json) — экспорт схемы этого изменения; секреты туда не включены. Обновлять его вместе с API.

## Восстановление

Не выполнять downgrade/restore рабочей БД при работающих backend/ASR. Приватный dump содержит полный снимок до auth. При откате сначала остановить свою инфраструктуру, восстановить архив в **отдельную пустую recovery-базу** подходящей версии PostgreSQL и проверить UUID/количество записей/связи. Затем выбрать согласованный код и подключение к проверенной восстановленной базе. Учесть, что восстановление старого снимка не включает записи после backup; не затирать их без отдельного решения.

Downgrade0009 сохраняет обычные бизнес-таблицы, но удаляет auth-сессии/подтверждения и новые User поля, поэтому не является штатным откатом активной эксплуатации. Если была подтверждена новая почта владельца, downgrade не заменяет её старым placeholder. Тестовые round-trip выполняются только на отдельной PostgreSQL базе с суффиксом _test.

## Проверки и границы

Есть тест миграции заполненной БД0008→0009 с сохранением UUID/текста/связей, тест явной подтверждённой привязки legacy-аккаунта и запрета присвоения первым корпоративным входом. Двухпользовательские проверки выполняются на PostgreSQL с настоящим кодовым auth-потоком и заменой только почтового транспорта/инференса. Проверка включила ручные UUID, admin, шаблоны, preview/candidates, refresh/аудиоповторы, фоновые результаты и восстановление ASR.

Рабочая среда остаётся локальной. До использования публичного HTTPS-шлюза нужно завершить реальную доставку SMTP и обновление Flutter, проверить запущенный защищённый процесс и указать точный доверенный IP прокси. PostgreSQL/Ollama/ASR не публикуются. Настройка самого VPS не входит в эту задачу.
