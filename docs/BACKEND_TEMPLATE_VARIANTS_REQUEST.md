# Backend: длинные тесты шаблонов и выбор варианта summary

Запрос Алексея от 23 октября 2026. Flutter работает в ветке mobile; backend-код не меняется мобильным агентом. Текущий контракт origin/backend 6273ea6.

## Пользовательский сценарий

В тесте шаблона можно выбрать одну из трёх заранее подготовленных вымышленных встреч или вставить свой транскрипт. Названия: «Планёрка команды», «Отчёт руководителю о проделанной работе», «Идеи для повышения вовлечённости сотрудников». Каждая встреча должна содержать 5000–15000 слов (именно слов, не символов). Приложение отправляет весь выбранный текст, без скрытой обрезки.

При просмотре результата пользователь меняет шаблон и запускает новую генерацию по тому же исходному транскрипту. Новый результат является кандидатом, а не второй сохранённой встречей. Кнопки назад/вперёд переключают уже готовые варианты без нового вызова LLM. «Готово» сохраняет только активный вариант. Ошибка, выход или отмена не должны портить исходное сохранённое summary.

## Ограничения актуального контракта

- POST /template-previews: максимум 12000 символов. Подготовленные длинные встречи не поместятся. Даже обычный ввод ограничен 100000 символов; число слов не равно числу символов или токенов.
- POST /transcripts/{id}/process после успешной генерации возвращает прежний ready, не запускает новую модель с другим шаблоном.
- Preview временный, хранится в памяти процесса до 15 минут, после перезапуска исчезает.
- PATCH summary изменяет текст, но сохраняет прежний template_snapshot. Принятие другого шаблона обычным PATCH оставит неверное происхождение документа.

## Что нужно реализовать

1. Согласовать и документировать лимиты длинного теста по фактическим размерам подготовленных текстов. Нужна проверка вместимости окна модели с учётом шаблона и ответа. Тихое усечение и отправка только первых 12000 символов запрещены. Если нужен способ обработки длинного входа, выбрать и проверить его явно; не менять размер контекста и параметры GPU незаметно.
2. Генерацию кандидата для существующего transcript/summary, включая уже успешно обработанный. Чтение того же проверенного текста; повторного ASR, дублирования transcript, встречи и папок не требуется. Полный неизменяемый снимок выбранного шаблона и параметров сохраняется с кандидатом. Генерация кандидата не изменяет сохранённое summary.
3. Polling кандидата и получение Markdown/navigation/error; стабильный ID операции, подтверждённый срок хранения и поведение при перезапуске/истечении. Дубликат одного пользовательского запуска после потери ответа не должен повторно вызывать LLM. Явный запуск с другим шаблоном — новый кандидат.
4. Атомарное принятие выбранного кандидата через «Готово»: content, template_snapshot и navigation согласованы; прежние summary ID, связь с источником и выбранные папки сохраняются для уже сохранённой встречи. Идемпотентный повтор принятия возвращает тот же подтверждённый результат. Проверка версии/конфликт предотвращает затирание параллельной ручной правки.
5. Для первой ещё не принятой генерации определить тот же принцип: в постоянную историю попадает только выбранный итог. Не внедрять подмену, при которой все кандидаты сначала создаются как отдельные встречи.
6. Определить завершение/отмену сессии выбора и очистку невыбранных кандидатов. При сетевой неопределённости Flutter сначала проверяет состояние; не удаляет исходное summary и не начинает всё с новым ключом.
7. Права доступа, ограничения очереди и GPU-сериализация сохраняются. Пользовательский текст не записывается в журналы. Встроенные примеры — синтетические, не пользовательская история.

Конкретные маршруты и схемы выбирает backend-агент; этот документ не задаёт выдуманные endpoints. Обновить docs/API_CONTRACT.md и docs/FLUTTER_HANDOFF.md, указать точные тела/ответы, лимиты, ошибки, повторы, миграции и необходимость перезапуска.

## Приёмка

- Полные три длинных текста обрабатываются без скрытого усечения; проверяются сведения в начале, середине и конце.
- Смена A→B→A и навигация по уже готовым вариантам не создают лишних вызовов Qwen и встреч.
- До «Готово» исходный документ не меняется; принятие B или A сохраняет ровно выбранный вариант с верным снимком шаблона.
- Ошибки LLM, сеть, потерянный ответ принятия, перезапуск, истёкший кандидат и конкурентная правка проверены.
- Аудио после GigaAM использует существующий источник без повторного распознавания.
- Прежние API и идемпотентность текстовых и аудиозапросов совместимы.

Backend-агент не меняет Flutter. После готовности передать мобильному агенту коммит, новый контракт и сведения о запущенной версии сервера.

Текущий максимум этих трёх примеров — 50263 символа; это не оценка числа токенов и не замена проверки вместимости контекста модели.
