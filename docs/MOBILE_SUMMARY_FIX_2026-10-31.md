### Цвет жирного текста

Подтверждено отдельное различие двух путей отображения: SummaryDocument назначал strong выбранный цвет документа, а VisualEditorBody использовал стандартный Quill bold без этого цвета. В тёмной теме текст оставался жирным, но выглядел белым/цветом основного текста. Причина — настройка представления редактора; потеря Markdown-маркеров не являлась подтверждённой причиной этого сценария.

Общий `documentBoldStyle(context)` теперь используется Markdown-просмотром, Quill customStyles.bold и просмотром защищённых блоков в редакторе. Учитываются цвет документа, тема и переключатель «Выделять жирный текст цветом». В Delta/Markdown/API не добавляются атрибуты цвета; предпочтение остаётся настройкой приложения. Специальный приглушённый стиль явно помеченных даты/участников сохранён.

Тесты проверяют **фактически отображаемые текстовые стили**, включая SelectableText/EditableText, а не только значение styleSheet. На сохранённом реальном тестовом ответе Qwen от 23 октября baseline воспроизводил стандартный цвет Quill при сохранённом FontWeight.bold; после правки оба редакторских пути проходят. Лог: `mobile/build/device-check/summary-color-repro.log`.

Полный тестовый цикл в обеих темах: папка → сохранённая встреча → новый шаблон → исходный/новый вариант → preview → визуальный редактор → правка → выключение/включение окраски → «Применить» → atomic accept → главная → повторное открытие обычного summary. На этом пути цвет после сохранения не теряется, форматирование сохраняется. Отдельно проверено обычное редактирование сохранённой встречи с сохранением и повторным входом в редактор.

## Атомарное сохранение с новым backend

`ApiClient.acceptSelection` передаёт candidate_id, исходный expected_version и только изменённые title/content одним POST. До HTTP контроллер сохраняет выбранного кандидата, точные правки и `accept_protocol=atomic-v1` в OperationStore. После этого изменение варианта/правок заблокировано до подтверждения результата, включая перезапуск.

Успех сохраняет полный SummaryOut как квитанцию. При потере ответа повторяется тот же JSON, включая наличие/отсутствие полей. Повтор получает неизменяемый receipt; поздняя чужая правка живого summary не перезаписывается. У новых операций **нет fallback accept → PATCH**, ни при сетевой ошибке, ни при 409/422. Старый backend отвергает новые поля: тест 422 подтверждает сохранность выбранного варианта и всех правок на диске, затем тот же запрос успешно повторяется после условного обновления сервера без отдельного PATCH.

Обычный SummaryEditor также передаёт полученный SummaryOut.version при PATCH. После успешного сохранения следующая правка использует новую версию. Конфликт не снимается отказом от CAS: введённый текст остаётся в редакторе. Это защита от молчаливой перезаписи; автоматическая замена внешнего документа не добавлялась.

## Старые незавершённые операции APK 0.1.2 и ранее

Отсутствие accept_protocol распознаётся как старый протокол, а не переводится в atomic-v1. Неизвестный исход старого accept повторяется **без title/content**, с прежним кандидатом/версией, затем квитанция сохраняется и актуальный summary читается через GET. Неприменённые старые ручные правки завершаются PATCH с CAS. Эта двухшаговая миграция разрешена только для старых checkpoints; новый протокол в неё не попадает.

В подготовленном diff воспроизведены две проблемы: (1) чужое изменение одного только title меняло version, но PATCH продолжал использовать старую версию receipt; (2) гонка GET→PATCH возвращала 409 и оставляла legacy-операцию frozen без доступного разрешения конфликта.

Исправление:

- После проверки неизменности затрагиваемых полей CAS защищает **версию только что прочитанного документа**. Чужое изменение другого поля сохраняется.
- Видимый конфликт поля или CAS-гонка сохраняют `edit_conflict`. Принятый кандидат, исходная квитанция и правки остаются на месте; повторное открытие не выполняет PATCH без решения пользователя.
- UI показывает «Повторить сохранение» и диалог подтверждения. Отмена ничего не перезаписывает. «Сохранить мои правки» фиксирует отдельный `edit_baseline`, затем повторяет проверку/CAS. Исходный receipt не переписывается новой baseline.
- Если ответ успешного PATCH потерялся, GET узнаёт уже применённые правки; второй PATCH не нужен. Неполный receipt старого формата читается безопасно.

Не создаются новые встреча, transcript, selection, ASR или Qwen ради восстановления. Source draft/checkpoint очищается только после подтверждённого завершения.

## Дополнение после публикации основного этапа

Основной этап опубликован коммитом `2cdb82c`. Последующее ревью координатора обнаружило узкий риск в добавленном CAS обычного SummaryEditor: сервер мог сохранить PATCH, ответ терялся, а локальная summary.version оставалась прежней. Повторная галочка получала 409, хотя отправленные правки уже присутствовали на сервере. Три новых baseline-регрессии воспроизвели потерю успешного ответа, недоступный GET и ввод во время запроса; лог `summary-cas-lost-repro.log`.

Исправление подготовлено отдельным последующим коммитом, без amend/force. Обычный редактор хранит точные название/содержание/версию неизвестного PATCH и сверяет GET после неопределённого исхода или CAS-конфликта. **Только совпадение обоих полей** подтверждает сохранение и обновляет локальную version. Если исходная версия ещё текущая, допустим повтор прежнего точного намерения под тем же CAS. Если версия изменилась и поля не совпадают, локальный текст и ошибка остаются; CAS не снимается.

Сверка обновляет сохранённую baseline и summary, но не заменяет title/content, набранные позже. После подтверждения предыдущего запроса flush отдельно сохраняет новый ввод с обновлённой версией. Если пользователь вернул текст к старой baseline, неизвестный запрос всё равно сначала разрешается. Явная отмена правок не оставляет скрытого повтора старого запроса.

Восемь новых проверок: потерянный успешный PATCH без дублирующей записи; потерянные PATCH+GET и последующий ввод; ввод в полёте; отдельные чужие изменения title/content; возврат текста к исходному; явная отмена; неизвестный запрос без серверного commit с точным повтором перед поздней правкой. После дополнения **266 тестов прошли**, анализ без замечаний. Неопределённое намерение обычного SummaryEditor сохраняется на время жизни редактора; постоянная offline-библиотека/перенос такого обычного ввода через смерть процесса не добавлялись. Durable atomic/legacy checkpoints выбора вариантов остаются отдельным механизмом.
