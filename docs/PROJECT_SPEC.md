# PROJECT_SPEC.md

# Проект: мобильный ассистент для обработки рабочих совещаний

## 1. Назначение

Мобильное приложение предназначено для фиксации, транскрибации, обработки, хранения и последующего использования результатов рабочих совещаний.

Основной пользователь — руководитель.

Главная ценность продукта:
- сокращение ручного протоколирования;
- выделение решений, задач, ответственных и сроков;
- быстрый доступ к истории встреч;
- возможность передавать исходный транскрипт другим пользователям, чтобы каждый создавал собственный summary по своему шаблону.

## 2. Текущий этап

Сначала реализуется тестовая версия.

Тестовая инфраструктура:
- мобильное приложение Flutter;
- backend на ПК разработчика;
- PostgreSQL на том же ПК;
- локальная ASR-модель на ПК;
- локальная LLM на ПК.

В дальнейшем локальные ASR/LLM должны быть заменяемы на корпоративные API без изменения пользовательских сценариев и без существенной переработки мобильного клиента.

## 3. Основные разделы приложения

### 3.1. Новая встреча

Первый и основной раздел.

Доступны четыре действия:
1. Записать встречу с микрофона.
2. Загрузить аудиофайл.
3. Загрузить или вставить готовый транскрипт.
4. Подключить источник видеоконференции — пока как задел на будущую интеграцию.

Основная кнопка визуально — «Записать встречу».

Перед записью пользователь может, но не обязан, указать:
- название;
- одну или несколько папок;
- шаблон обработки;
- дополнительные настройки.

После записи:
1. аудио отправляется на backend;
2. backend передаёт его в ASR;
3. формируется транскрипт;
4. при необходимости пользователь редактирует транскрипт;
5. транскрипт отправляется в LLM вместе с шаблоном;
6. формируется summary;
7. summary сохраняется;
8. исходный транскрипт также сохраняется.

Если название и папки не были указаны заранее, LLM предлагает название и подходящие папки из существующих.

По умолчанию пользователь подтверждает предложение. В настройках можно включить автоматическое сохранение по предложению ИИ без дополнительного подтверждения.

### 3.2. Встречи

Вверху — поиск. Ниже — дерево пользовательских папок; внутри папок — summary встреч.

Один summary может находиться сразу в нескольких папках. В MVP отдельный раздел «Последние встречи» не нужен.

### 3.3. Инструменты

На первом этапе содержит работу с шаблонами:
- системные шаблоны;
- пользовательские шаблоны;
- создать шаблон;
- редактировать пользовательский шаблон;
- удалить пользовательский шаблон;
- дублировать системный шаблон в пользовательский;
- предпросмотр шаблона;
- тестировать шаблон на коротком транскрипте;
- выбрать шаблон по умолчанию.

### 3.4. Профиль / настройки

Аккаунт:
- просмотр email;
- смена пароля.

Настройки обработки:
- шаблон по умолчанию;
- показывать транскрипт перед отправкой в LLM;
- обезличивать персональные данные перед отправкой в LLM;
- уровень детализации summary;
- автоматически сохранять предложенные LLM название и папки.

Уведомления:
- общий переключатель;
- транскрипт готов;
- summary готов;
- получена встреча от другого пользователя;
- ошибка обработки.

## 4. Работа с summary

Summary принадлежит конкретному пользователю.

Пользователь может:
- читать;
- свободно редактировать;
- редактирование сохраняется автоматически;
- удалить свой summary;
- передать встречу другому пользователю;
- переформатировать summary по другому шаблону.

При смене шаблона новый summary строится заново из исходного транскрипта.

Перед заменой текущего summary пользователь должен увидеть новый результат и подтвердить замену.

История версий в MVP не хранится.

## 5. Передача встречи другому пользователю

Передача выполняется по email.

Пользователь нажимает «Поделиться» у своего summary и вводит email получателя.

Важно:
- чужой summary не становится рабочим summary получателя;
- физическая копия транскрипта не создаётся;
- получателю открывается доступ к исходному transcript_id.

Сценарий:
1. отправитель указывает email;
2. backend находит получателя;
3. создаётся запрос передачи;
4. получателю приходит уведомление;
5. получатель принимает или отклоняет;
6. при принятии получатель выбирает свой шаблон;
7. из общего транскрипта создаётся его собственный summary;
8. он выбирает собственное название и папки либо использует предложения LLM.

## 6. Основные продуктовые правила

- Один исходный транскрипт соответствует одной реальной встрече.
- У одного транскрипта может быть несколько summary — по одному на каждого пользователя, которому он доступен.
- Для одного пользователя и одного transcript_id в MVP существует один актуальный summary.
- Название встречи является персональным свойством summary, а не транскрипта.
- Папки персональные.
- Один summary может находиться в нескольких папках.
- Транскрипт хранится централизованно.
- Аудиофайл после успешной транскрибации постоянно не хранится.
- Офлайн-режим в MVP не реализуется.
- Мобильный клиент не подключается напрямую к PostgreSQL.
- Мобильный клиент не хранит ключи ASR/LLM.
- Вся серверная бизнес-логика проходит через backend.

## 7. Статусы обработки

Минимальный набор:
- uploaded;
- transcribing;
- transcript_ready;
- summarizing;
- ready;
- error.

Если включён просмотр транскрипта перед LLM, обработка останавливается после transcript_ready до подтверждения пользователя.

## 8. Поиск

Для MVP:
- поиск по названию;
- поиск по summary;
- фильтрация через папки.

Расширенный поиск по транскриптам, задачам, решениям и другим полям можно добавить позже.

## 9. Что не входит в первую тестовую версию

Пока не требуется:
- офлайн-режим;
- история версий summary;
- сложная ролевая модель;
- прямые интеграции с видеоконференциями;
- семантический поиск;
- совместное редактирование одного summary;
- хранение аудио после транскрибации;
- полноценная production-инфраструктура;
- Kubernetes и сложный DevOps.

## 10. Критерий успешной первой версии

Пользователь с телефона может:
1. зарегистрироваться / войти;
2. записать или загрузить аудио;
3. получить транскрипт;
4. получить summary через локальную LLM;
5. увидеть сохранённый summary в своей папке;
6. отредактировать его;
7. переформатировать другим шаблоном;
8. передать транскрипт другому зарегистрированному пользователю;
9. получатель может принять его и создать собственный summary.
