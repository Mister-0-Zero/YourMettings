# Просмотр и выбор summary — 27.10.2026

## Поведение

Во время первой и повторной генерации остаются выбранный шаблон, вращающийся индикатор и «Qwen обрабатывает транскрипт». Скрыты линейный прогресс, выбор шаблона, кнопка запуска, счётчик вариантов и кнопки сохранения. Ошибки показывают пояснение и возможность повтора.

Готовый результат автоматически сменяет экран ожидания. Это форматированный Markdown-просмотр с кнопками редактирования и общей галочкой «Сохранить встречу». Выбор шаблона сразу запускает новую генерацию. Назад/вперёд появляются при наличии предыдущего результата; они используют уже готовые варианты, без нового Qwen.

Редактор использует прежний VisualDocument/Quill. «Применить» сохраняет правки конкретного варианта на устройстве и возвращает в просмотр. У каждого варианта отдельные правки названия/Markdown, которые сохраняются вместе с незавершённой операцией. Общая галочка принимает именно открытый вариант и его шаблон. После подтверждённого сохранения и локальной очистки открывается главная вкладка «Новая встреча», в том числе при входе из ранее сохранённой встречи.

## Сохранение и API

Backend и контракт не менялись. Кандидаты Qwen неизменяемы. Поэтому финальное сохранение выполняет существующий accept, затем при наличии ручных правок частичный PATCH обычного summary. Только изменённые поля отправляются в PATCH; правка содержания не отправляет старое название.

До HTTP фиксируются candidate_id и конкретные правки. После accept фиксируется квитанция; при сбое PATCH повтор не создаёт ещё одну встречу и не запускает Qwen. Прежде чем повторять PATCH, читается актуальный документ: уже совпадающие правки считаются сохранёнными, обнаруженные другие правки требуют явного подтверждения замены. Для исходного сохранённого summary сравнивается baseline при открытии, а не произвольный свежий GET после отмены выбора. При ошибке подтверждённый выбор остаётся закреплён, правки доступны для исправления и повтора, переход на главную не выполняется.

Предел существующего API: accept + PATCH не являются одной транзакцией; до успешного PATCH на сервере может быть принят исходный вариант Qwen. Незавершённое применение правок остаётся на устройстве до завершения. PATCH по контракту использует last-write-wins без CAS, поэтому проверка GET обнаруживает уже видимые конкурентные изменения, но не устраняет узкую гонку GET→PATCH. Атомарное принятие редактированного кандидата потребовало бы отдельного изменения backend; в этой задаче оно не выполнялось.
