## Проблема и результат

Раньше accept принимал только candidate_id/expected_version. Если пользователь редактировал выбранный результат, клиенту требовался отдельный PATCH: принятие и правки не были одной операцией. Для прямого PATCH также не было необязательной проверки исходной версии.

Теперь выбранный кандидат, ручные title/content, версия, состояние источника/аудиосессии и неизменяемая квитанция принятия записываются одной транзакцией. Повтор того же запроса после потерянного ответа возвращает прежнюю квитанцию и не затирает последующие изменения. Прямой PATCH поддерживает compare-and-set по version под row lock.

Никакие offline-функции, новые сценарии папок или автоматический ASR→Qwen не добавлялись. Повторные ASR/Qwen для принятия и ручных правок не запускаются.

## Точный контракт для Flutter

### Принятие выбранного результата

`POST /api/v1/summary-selections/{id}/accept`:

```json
{
  "candidate_id":"9eb86384-b41e-4727-9f72-cb78f33106c4",
  "expected_version":"79d40b54f1fb56bf40ed2431d1329dc1dccf86244443a40aec04b33115db5eb38",
  "title":"Итоговое название",
  "content":"## Решения\nВыбранный документ с ручными правками."
}
```

- candidate_id обязателен. title/content необязательны и независимы; опущенное поле оставляет название существующего summary/новой Selection либо берёт текст кандидата.
- Title нормализуется trim, затем 1–200 символов. Content — непустой/не из одних пробелов, до **200000 символов**, сам текст не обрезается. Явный null для edits запрещён →422.
- Для существующей встречи expected_version обязателен и равен **исходному summary_version Selection**. Для новой — отсутствует либо null. Формат непустой версии — 64 lowercase hex. Ошибочная/устаревшая версия существующей встречи →409 summary_version_conflict.
- Успех — **200 SummaryOut**: итоговые title/content, navigation по отредактированному Markdown, version, прежние template_snapshot/generation_options выбранного кандидата. У существующей встречи сохраняются ID, источник и текущие folder_ids. Папки не передаются через accept.
- Идентификатор операции — Selection, отдельный Idempotency-Key для accept не нужен. До отправки Flutter сохраняет **полный неизменяемый JSON**, а не только candidate_id.
- Для новой квитанции повтор сравнивает candidate_id, expected_version и наличие/значения title/content. Одинаковый запрос →200 точно сохранённый первый ответ. Два конкурентных одинаковых запроса получают ту же квитанцию.
- Тот же кандидат с другими edits/версией/наличием поля →409 idempotency_conflict. Другой кандидат →409 selection_closed. Даже явно совпадающий с кандидатом content отличается от отсутствующего content. Название сравнивается после trim; omitted/null expected_version новой встречи эквивалентны.
- После позднего ручного PATCH повтор accept всё ещё возвращает первоначальную квитанцию. Текущее состояние — отдельный GET summary. Не перепосылать старые правки с новой версией автоматически.
- Для исторических квитанций до 0010 (accepted_request_hash=NULL) сохраняется прежний retry того же candidate_id без title/content; новые edits дают409. Полный fingerprint старого запроса задним числом не восстанавливается.
- Дополнительные ошибки: чужая/неизвестная сессия или кандидат другой открытой сессии404; candidate_not_ready409; source_conflict409; закрытая cancelled/expired410; неверные параметры422. Ошибки имеют обычный error envelope.

### Прямой PATCH сохранённого summary

`PATCH /api/v1/summaries/{id}` принимает title и/или content, а также **необязательный expected_version из GET SummaryOut.version**. Новый Flutter должен передавать его. Хотя бы одна правка обязательна; явный null для любого поля, включая expected_version, запрещён →422.

Проверка и запись под row lock; несовпадение →409 summary_version_conflict без частичной записи. Без expected_version сохранён legacy last-write-wins. Папки, источник и параметры шаблона PATCH не меняет. Каждая успешная запись увеличивает ревизию: A→B→A не восстанавливает старую version.

PATCH не имеет квитанции accept. При потерянном ответе повтор со старой версией может вернуть409; клиент делает GET, сверяет сохранённые поля с замороженным запросом и сохраняет локальный текст до разрешения неопределённости. Молчаливое повторение старой правки с новой версией запрещено клиентским протоколом.

## Порядок выпуска: backend до APK

Это **инструкция к последующему разрешённому развёртыванию**, команды на production не выполнялись.

1. Общий diff backend/mobile проверен координатором, подтверждённых незакрытых находок по его независимому read-only ревью нет; публикация разрешена. Код и этот отчёт коммитятся и отправляются в backend без main merge. Точный hash и факт push указываются в итоговом сообщении, коммит также виден в истории отчёта.
2. Проверить рабочую конфигурацию, доступ к production-БД и наличие окна обслуживания. Если срок demo-доступа истёк, отдельно согласовать продление/ротацию либо другой рабочий режим: эта доработка не отключает защиту и не продлевает ключ автоматически. Истёкший demo mode может остановить загрузку Settings ещё до запуска Alembic/сервера.
3. Сделать приватный проверенный backup production-БД. Перенести только согласованные файлы/коммит в рабочий backend, сохранив .env, окружение, локальные ресурсы и чужие изменения. Дождаться завершения текущих пользовательских обработок перед перезапуском.
4. Из **рабочего backend/** существующим `.venv\Scripts\python.exe` выполнить `-m alembic current`, затем **`-m alembic upgrade head`** и `-m alembic check`. Ожидаемая ревизия — **0010**. Nullable-колонка совместима с прежними квитанциями, backfill личных данных не требуется.
5. Только после миграции перезапустить **один backend** на новом коде прежним launcher, проверить PostgreSQL и HTTP с действующими credentials. ASR-worker, Ollama, туннель, Firewall/VPN и мобильные данные ради этой миграции не менять.
6. Провести интеграционную проверку отдельной синтетической встречи новым клиентом: edited accept, повтор после неопределённого ответа, CAS PATCH/409, обновлённые title/content/version/navigation. Не использовать реальные встречи владельца как тестовые объекты. Проверить согласованность `/openapi.json` с сохранённым экспортом.
7. **Только после готовности backend с 0010/API** распространять новый APK с атомарным протоколом. Старый backend не знает title/content accept и expected_version PATCH и вернёт422; установка APK раньше API недопустима.

При необходимости отката не выполнять автоматический downgrade production. Он удаляет fingerprints новых accept, хотя сами квитанции/summary сохраняются. Возврат старого кода с оставленной nullable-колонкой и решение об откате схемы — отдельный согласованный операционный шаг; backup обязателен.
