# Восстановление диктофона после удаления — 28.10.2026

Ветка: mobile. Исходный HEAD: 2e8e7b7. Backend/VPS не изменялись. Источник диагностики: `C:/Users/Алексей/Documents/ChatGPT/YourMettings/FLUTTER_AUDIO_DELETE_BUG.md` и два указанных в нём скриншота.

## Что подтверждено

Из переданной диагностики: backend уже удалил аудиосессию владельца; GET возвращает 404, подтверждённый повтор DELETE — 204. Эти серверные проверки выполнены перед передачей задачи, в этой работе заново не заявляются.

В старом мобильном коде воспроизведён дефект владения: `start()` вызывал `_receive(journal.data)` без `connection_scope`. При активном demo-подключении `_receive` устанавливал `_foreignOwner=true`; флаг не снимался даже после корректного `done`. Реальный coordinator с реальным journal/engine завершал release ошибкой `Review handoff not acknowledged` и продолжал считать диктофон занятым. Это соответствует сочетанию «journal уже done, но новая запись запрещена».

Точный runtime-путь на HONOR не получен: устройство отсутствовало в ADB; владелец сообщил, что сейчас подключить его не может. Не утверждается, что именно этот exception был на телефоне. Исправлены также выявленные гонки остановки службы и доставки подтверждений.

## Исправление

- Локальный подготовленный journal помечается текущим scope и передаётся как локальный источник. Подтверждённый снимок верного владельца снимает ошибочный флаг чужой записи.
- Перед отправкой команды проверяется наличие service. Если служба уже остановилась, coordinator присоединяет локальный engine. При потере ответа от остановившейся службы состояние сверяется с journal.
- Команда связана со scope, экземпляром service и session ID. Service проверяет владельца до выполнения. ACK содержит итоговый snapshot; ожидаемая сессия берётся из самой команды, а не из уже изменившегося `state.id`. Поддержаны оба порядка прихода done/ACK.
- Поздний snapshot освобождённой сессии не возвращает блокировку и не заменяет состояние новой записи. Снимки service не переписывают состояние уже присоединённого локального engine.
- Перед обычной отправкой/complete/ASR retry проверяется durable delete/handoff целевой сессии. При восстановлении подтверждённого удаления не отправляются старые POST/upload и не запускается Qwen.
- Сохраняются прежние строгие проверки release: правильная сессия, безопасная фаза, все ACK, отсутствие оставшихся WAV. Чужие файлы/записи не удаляются, общий storage не очищается.
- `serverDeleted` после 204 фиксируется до локального release. При потере ответа/ошибке записи квитанции сохраняется delete intent; восстановление повторяет DELETE того же session ID. GET 404 не используется как разрешение удалить локальные данные.
- Startup восстанавливает как handoff, так и deletePending/serverDeleted. Сопоставление старого recovery проверяет владельца; другая принятая операция сохраняется даже при оставшейся старой привязке. Повторное восстановление сериализовано.
- В черновиках есть явная карточка «Завершить удаление». На экране транскрипта удаление выделено отдельным состоянием с retry; в диктофоне доступно завершение оставшейся операции даже при done без session ID. Ожидающее удаление не предлагает обработку Qwen или редактирование удалённого текста.
- Ошибки различают отсутствие подтверждения сервера и незавершённую локальную очистку после 204. Диагностика содержит только stage/type/code, без ключей, речи и полного HTTP.

Схема локальных файлов и secure storage не менялась; отдельной миграции, очистки данных или hardcode ID проблемной встречи нет. Существующий durable checkpoint владельца обрабатывается общим восстановлением при открытии обновлённого приложения.
