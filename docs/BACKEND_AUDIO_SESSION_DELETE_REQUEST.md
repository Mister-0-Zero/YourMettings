# Задание backend-агенту: явное удаление незавершённой аудиовстречи

Ты — backend-разработчик YourMettings. Работа выполняется в backend-ветке по правилам проекта; Flutter-код и mobile-worktree не изменяй. За основу возьми текущий docs/API_CONTRACT.md (мобильный клиент сейчас использует 16deb09). Не выполняй merge в main. Не останавливай активные пользовательские процессы без необходимости; сообщи, потребуется ли перезапуск после завершения.

## Пользовательский сценарий

На проверке распознанного транскрипта нужны три действия:

1. Продолжить редактирование — остаться с текущим текстом.
2. Сохранить черновик и выйти — сохранить текст/название/настройки, освободить текущий диктофон для новой записи; позже открыть старый черновик в разделе «Пространство». Возобновление использует прежние audio_session_id/transcript_id, не запускает повторно ASR/Qwen. Локальные черновики реализует Flutter; серверный CRUD черновиков для этого не требуется.
3. Удалить встречу — после отдельного подтверждения действительно удалить незавершённую аудиовстречу с сервера. Клиент очищает свой черновик только после подтверждённого результата. Удаление только локального указателя нельзя выдавать за удаление встречи.

Сейчас контракт предоставляет DELETE summaries и folders, но не удаление audio-session до confirm. Создавать summary ради удаления запрещено.

## Узкое дополнение API

Исследуй текущие модели, FK, очистку аудиофайлов, ASR-worker, блокировки confirm/upload/retry и правила ownership. Добавь явное удаление незавершённой аудиосессии, например DELETE /api/v1/audio-sessions/{id}?confirm=true. Выбери окончательные метод/параметры и коды согласно существующим соглашениям и точно опиши их в API_CONTRACT.md.

Минимально нужен безопасный путь для ready_for_review до confirm: ASR закончен, Qwen ещё не запускался. Не расширяй автоматически область на активную запись/ASR/Qwen. Для неподдерживаемого/активного состояния — документированный конфликт с сохранением данных. Поведение completed-сессий согласуй с существующим удалением summary; нельзя безусловно удалить опубликованный результат или общий источник через новый обходной endpoint.

Требования:

- Явное подтверждение обязательно; при его отсутствии данные остаются целыми.
- Удаление проверяет владельца/доступ согласно текущему тестовому пользователю. Чужая/неизвестная сессия не раскрывается.
- После успеха незавершённая сессия и её неиспользуемые транскрипт/части/технические данные удалены либо необратимо помечены удалёнными согласно выбранной схеме. Другие встречи, summary и внешние зависимости не повреждаются. Для связанных/общих объектов предпочти явный конфликт, если полное удаление невозможно безопасно.
- Согласуй удаление с конкурентными confirm, upload, retry и поздним результатом worker. Недопустимы частичное удаление, воскрешение объекта worker-ом или удаление данных другой встречи.
- Очистка файлов согласована с commit БД; ошибка файловой операции не должна оставлять ложное подтверждение удаления либо ломать worker. Опиши фактическую семантику удаления аудио, если его TTL-очистка уже произошла.
- Потеря ответа и повтор DELETE должны иметь безопасную документированную семантику (204 либо 404 после первого успеха согласно соглашениям). Уточни поведение старого Idempotency-Key создания после удаления: Flutter не будет повторять создание намеренно удалённой сессии.
- При сетевой ошибке/5xx клиент сохраняет черновик и предлагает повторить; API не должен требовать молчаливого удаления локальных данных.
- Новые API для почты, sharing, шаблонов, синхронизации черновиков и авторизации не добавляй.

## Проверки

Проверь успешное удаление ready_for_review без summary, обязательность подтверждения, права/неизвестный ID, повтор после потерянного ответа, конфликт неподдерживаемого состояния, сохранность чужих/связанных объектов и гонку с confirm. Проверь поздний результат ASR-worker, если это состояние реально допускается выбранным endpoint. Старые тесты аудиосессий и удаления summary должны проходить.

## Результат для Flutter-разработчика

Сделай commit и push в backend после проверок. Сообщи hash, точный endpoint/параметры/ответы/ошибки, правила повторов, допустимые состояния, способ проверки исчезновения объекта, необходимость миграции/перезапуска и результаты тестов. Обновлённый docs/API_CONTRACT.md остаётся единственным источником API для мобильной реализации.

Мобильная часть пока НЕ переведена на несколько черновиков и новое действие удаления. Планируемая схема: отдельный каталог и контекст каждого черновика, закреплённые ID, отдельный указатель активного захвата, сохранение перед освобождением диктофона, восстановление перехода после сбоя. Открытие/завершение старого черновика не должно отправлять done текущей новой записи. Готовые серверные встречи не копируются в локальную библиотеку.
