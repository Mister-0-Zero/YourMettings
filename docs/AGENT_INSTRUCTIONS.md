# AGENT_INSTRUCTIONS.md

# Инструкции coding-агенту

## 1. Источник истины

Перед существенными изменениями прочитать:
1. PROJECT_SPEC.md
2. ARCHITECTURE.md
3. DATA_MODEL.md
4. IMPLEMENTATION_PLAN.md

Если документы противоречат коду, сначала указать противоречие и предложить исправление. Не молча менять продуктовую логику.

## 2. Основной принцип

Строить рабочий вертикальный срез, а не писать десятки абстракций заранее.

Первый приоритет:

```text
Flutter -> FastAPI -> PostgreSQL -> local ASR -> local LLM -> PostgreSQL -> Flutter
```

## 3. Не переусложнять

Без необходимости не внедрять:
- микросервисы;
- Kubernetes;
- Redis;
- Celery;
- Kafka;
- event sourcing;
- CQRS;
- сложную Clean Architecture с десятками слоёв;
- отдельную БД на пользователя;
- прямой доступ Flutter к PostgreSQL.

Backend на первом этапе — один FastAPI-сервис.

## 4. Сохранить заменяемость интеграций

ASR и LLM должны быть за адаптерами/интерфейсами.

Нужно иметь возможность переключить local implementation на remote API через конфигурацию, а не переписывать бизнес-логику.

## 5. Работа по этапам

Для каждого этапа:
1. кратко описать план;
2. реализовать;
3. запустить тесты;
4. показать результат;
5. только потом идти дальше.

## 6. Тесты

Backend:
- unit tests для бизнес-правил;
- API tests для основных endpoints;
- database integration tests для критичных сценариев.

Особенно проверить:
- пользователь не видит чужие summary;
- пользователь не может положить summary в чужую папку;
- accepted share даёт доступ к transcript;
- rejected/pending не даёт доступа;
- для user + transcript не создаётся второй active summary;
- удаление summary не удаляет используемый transcript.

Flutter:
- минимум smoke/widget tests для основных экранов;
- не блокировать MVP чрезмерным количеством UI-тестов.

## 7. Ошибки

Ошибки ASR/LLM не должны приводить к потере данных или зависанию job.

processing_job переводить в error с читаемым error_message.

Пользователь должен иметь возможность повторить обработку.

## 8. Безопасность

- пароли только в hash;
- никаких секретов в Flutter;
- никаких DB credentials в Flutter;
- `.env` в `.gitignore`;
- авторизация и права проверяются на backend;
- не доверять user_id, присланному клиентом, если его можно определить из token/session.

## 9. API

Конкретные endpoint names заранее не зафиксированы намеренно.

Спроектировать небольшой REST API самостоятельно, придерживаясь бизнес-правил.

Перед первой реализацией API показать предлагаемый список endpoints владельцу проекта.

## 10. UI

Не заниматься декоративной полировкой до работающего end-to-end сценария.

Сначала функциональный UI:
- вход;
- новая встреча;
- встречи/папки;
- summary;
- инструменты/шаблоны;
- профиль.

## 11. Решения, которые нельзя менять без согласования

- PostgreSQL — основная БД.
- Backend обязателен.
- Один transcript является общим источником.
- Summary персонален пользователю.
- Один summary на user + transcript.
- Один summary может быть в нескольких папках.
- Папки персональные и могут быть вложенными.
- Шаринг передаёт доступ к transcript, а не копию чужого summary.
- Offline MVP не нужен.
- Аудио после успешного ASR постоянно не хранится.
