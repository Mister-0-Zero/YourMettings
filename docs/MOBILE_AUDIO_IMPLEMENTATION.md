# Диктофон и GigaAM: реализация и границы проверки

Источник API — `docs/API_CONTRACT.md`, обновлённый из `origin/backend` на `e5ed87c`. Backend не изменяется. Этот документ описывает мобильную реализацию; фактические результаты испытаний находятся в отдельном отчёте.

## Запись

Используются `record 7.1.2` и `flutter_foreground_task 11.0.3`. Первый предоставляет нативный захват Android AudioRecord / iOS AVFoundation, PCM-поток, паузу и возобновление. Фоновую Android-службу предоставляет второй пакет. Сам `record` фоновой службы не создаёт: [возможности](https://pub.dev/packages/record), [background recording](https://github.com/llfbandit/record/blob/master/doc/bg_recording.md).

Микрофон запускается один раз. Выход — PCM16, mono, 16000 Hz. `PcmChunkWriter` последовательно записывает каждый полный PCM-сэмпл ровно в один независимый WAV. Около серверного `chunk_target_seconds` ищется тихий участок длительностью 400 мс; `max_chunk_seconds` и `max_upload_bytes` ограничивают ожидание. Перекрытие равно нулю. На границе файлов микрофон не останавливается. Заголовок каждого завершённого WAV содержит его фактический размер. Длительность и глобальная шкала вычисляются из количества PCM-сэмплов, паузы из них исключены.

Память не содержит аудио всей встречи. Входные буферы небольшие; файлы отправляются потоком с ограничением в один запрос одновременно. Запись файла и вычисление его SHA256 отделены от HTTP-ожидания. На Android захват и файловый журнал работают в отдельном Flutter isolate службы; блокировка UI не останавливает их.

Android: `RECORD_AUDIO`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE`, `WAKE_LOCK`; тип службы `microphone`, постоянное уведомление. Старт только после действия пользователя на видимом экране и выдачи разрешений. Автостарт после перезагрузки/убийства отключён. Служба не держится бесконечно после окончания записи: после доставки/при офлайн-завершении очередь передаётся приложению. [Ограничения Android](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

`record_android 2.2.0` требует Activity даже при `hasPermission(request:false)` и возвращает false в service engine. Поэтому проверка/запрос выполняются в UI; служба использует результат этого пути. Проверки разрешения Android при старте microphone FGS и при открытии AudioRecord остаются обязательными и не обходятся.

iOS: реальный `record`/AVAudioSession, `NSMicrophoneUsageDescription`, `UIBackgroundModes=audio`; периодический background-fetch не используется как замена записи. Прерывание микрофона переводит приложение в видимую паузу. Есть описание доступа к локальной сети и узкое ATS-разрешение LAN. [Apple: фоновая запись](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/record), [локальная сеть](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking).

После окончания/при паузе iOS может приостановить процесс и обычные HTTP-запросы. Неотправленные файлы остаются на диске; повторы возобновляются при возвращении приложения. Отправка после принудительного завершения через native background URLSession здесь не реализована; самостоятельное пробуждение выгруженного приложения не обещается. Во время активной аудиосессии отправка выполняется параллельно захвату.

## Сохранность

В Application Support есть одна активная запись `active-audio/`, а не библиотека встреч:

- `session.json`: стабильный ключ создания, серверный ID, принятые ограничения, параметры, состояние записи, последовательность/время/ACK каждого файла;
- `N.wav`: текущий ремонтируемый WAV и ещё не подтверждённые файлы;
- `audio-review-recovery.json` рядом: редактируемый транскрипт либо принятый `transcript_id` и параметры Qwen.

Текстовый черновик `meeting-recovery.json` независим. Принятие аудиовстречи не стирает вставленный текст другой встречи.

Файл сначала закрывается и синхронизируется, затем публикуется в журнале для отправки. Журнал заменяется атомарно через временный файл. Текущий WAV синхронизируется примерно каждую секунду; после аварии заголовок восстанавливается по фактической длине файла. После убийства процесса запись честно показывается прерванной, микрофон сам не включается. Сохранённое аудио можно отправить без повторной записи. Звука, не дошедшего из нативного capture-буфера на диск до аварии, восстановить нельзя; абсолютная сохранность последнего буфера при отключении питания не обещается.

После `accepted=true`, `safe_to_delete_local=true`, совпадения SHA256 и номера ACK записывается в журнал, затем файл удаляется. Потерянный ответ приводит к отправке тех же байтов с теми же метаданными, а не к созданию новой сессии. Сбой записи ACK не разрешает удаление файла. Остаток после аварии между сохранением ACK и удалением удаляется при восстановлении.

Пауза не закрывает файл и не расходует номер фрагмента. Автоматические повторы сети/5xx имеют задержку до 60 секунд. Ошибки файла/конфликта не заменяют байты молча: файл сохраняется, предлагается явный повтор. Таймаут HTTP прерывает запрос, а не запускает неограниченное число параллельных отправок.

## API и проверка текста

1. До старта микрофона сохраняются стабильный ключ и параметры `POST /audio-sessions`; backend возвращает действующие ограничения.
2. Закрытые WAV отправляются сырыми байтами в `/chunks` с номером, временем, длительностью и SHA256.
3. После завершения и подтверждения всех файлов вызывается `/complete` с окончательным числом частей.
4. `/audio-sessions/{id}` опрашивается автоматически; готовый полный текст читается через `/transcripts/{id}`.
5. Существующая форма используется повторно: название, весь текст, папки и настройки. Изменения сохраняются локально до явного подтверждения.
6. Нажатие «Подтвердить и создать summary» сначала PATCH-ит полный текст, перечитывает сессию и сверяет hash с показанным текстом, затем вызывает `/confirm`. При предупреждениях стыков требуется отдельное подтверждение их проверки.
7. Дальше используются существующие polling Qwen, просмотр/редактор summary и «Принять». Для первой обработки аудио `/transcripts/process` не вызывается. Ошибка уже принятого Qwen повторяется существующим endpoint по известному ID.

Повтор `/confirm` после потерянного ответа сначала обнаруживает completed и возвращается к той же обработке. Принятый ID сохраняется до перехода к экрану результата. Ошибки оставляют редактируемый черновик. Автоматического подтверждения Qwen нет.

## Реальные ограничения

- API ограничивает сессию `max_chunks` (текущий пример 240), длительность/байты файла, размер общего транскрипта. Бесконечная серверная встреча невозможна. При достижении границы числа файлов захват останавливается с объяснением; приложение не создаёт вторую встречу автоматически.
- Первый запуск записи требует доступного backend для получения актуальных ограничений и создания сессии. Отсутствие сети после старта не останавливает захват. Офлайн-старт без ранее согласованных ограничений в этой версии не обещается.
- Неисправимый `timeline_mismatch`, пустая речь и превышение общего текста не исправляются повтором тех же ASR-фрагментов; соответствующая кнопка не выдаётся за работающее исправление.
- Предел дискового пространства реален; ошибка сохранения останавливает микрофон, оставляет доступные файлы и показывает ошибку. Тест использует управляемый сбой записи, а не заполнение пользовательского диска.
- Речь может распознаться неправильно или не попасть в микрофон из-за расстояния/громкости. Сэмпловая непрерывность файлов не гарантирует точность ASR; полный текст проверяется перед Qwen.
- Сборка и физическое испытание iOS требуют macOS/Xcode/iPhone; на Windows они не выполнены.

## Чек-лист физического iOS-испытания

1. Собрать Runner в актуальном Xcode, проверить подпись, capabilities Audio и доступ LAN.
2. Выдать/отказать разрешениям микрофона и сети; отказ должен сохранять данные и давать повтор.
3. Записать 30 минут с несколькими паузами; проверить три и более границы WAV, таймер и расход памяти.
4. Другая программа, Home, блокировка/выключенный экран; запись и уведомление системы о микрофоне должны соответствовать действительности.
5. Входящий звонок/смена аудиомаршрута: явная пауза или остановка, отсутствие молчаливой потери речи.
6. Отключить сеть, закончить запись, свернуть и повторно открыть приложение: очередь сохраняется, повторы не дублируют сессию.
7. Принудительно завершить процесс с открытым файлом, запустить снова: восстановить аудио, показать остановку; не запускать микрофон автоматически.
8. Пройти GigaAM → редактирование → подтверждение → Qwen → summary → «Принять»; проверить один transcript/summary и возврат к новой встрече.
