## Результат

В сохранённом summary появились отдельные действия **«Переместить»** и **«Добавить в другую папку»**. Они также доступны из меню конкретной встречи в списке папки; название по-прежнему открывает документ. Настоящий путь `Встречи → папка → summary` передаёт `sourceFolderId` в экран документа, включая вложенные папки. Из generic/new summary без такого контекста нет неоднозначного «переместить всё»: остаются добавление и прежние «Папки встречи».

- Из A,C **добавить в B** → A,B,C. Уже назначенные папки отмечены и заблокированы от снятия в этом действии. Есть короткое пояснение: «Это одна встреча: изменения будут видны во всех её папках».
- Из A,C **переместить из A в B** → B,C. Из A,B,C переместить в уже назначенную B → B,C без дубля. Выбирается одно назначение, исходная A недоступна как назначение; другие связи сохраняются.
- Отступы вложенности, полный путь в tooltip/семантике, создание папок/подпапок сохранены. Нижние кнопки переносятся на узком экране, добавлена явная отмена. Подтверждение невозможно при неуспешном refresh дерева, неизвестных выбранных IDs или нарушении лимита 1–100.
- При успехе обновляются связи текущего документа, контроллер и дерево; после возвращения — содержимое/total папки. Если старая пагинация ещё в полёте, refresh дожидается её и затем перечитывает первую страницу, чтобы старый ответ не вернул уже перемещённый документ.

Операция не копирует summary/transcript, не запускает Qwen/ASR и не делает PATCH содержания.

## Контракт и конкурентные изменения

Использован опубликованный backend-коммит **`1f7f23d`**. В мобильный worktree перенесён его `docs/API_CONTRACT.md`; новая [памятка](FLUTTER_FOLDERS_HANDOFF.md) соответствует тому же коммиту, ссылка на OpenAPI указывает на опубликованный backend blob. Merge/cherry-pick серверного кода не выполнялись. Единственный источник API-требований — [API_CONTRACT.md](API_CONTRACT.md#размещение-одного-summary-в-папках).

Все подтверждения новых UI-действий, включая неизменённый набор в «Папки встречи», отправляют существующий `PUT /summaries/{id}/folders` с **полными target и expected_folder_ids**. Expected берётся из свежего GET перед picker; он не подменяется автоматически после 409. Optional поле API-клиента оставляет совместимость старым вызывающим сторонам, но новый UI его всегда передаёт.

**409 `summary_folders_conflict`** → GET актуальных связей, понятное сообщение, сохранённое в состоянии экрана намерение и явная кнопка «Проверить выбор папок». Новый запрос возможен только после повторного выбора/подтверждения пользователем. Предложение повторного выбора содержит прежний delta, сохраняя новые внешние размещения и не восстанавливая снятые другим клиентом старые связи. Никакого unconditional PUT или автоматического POST замены нет. Пока пользователь остаётся на экране, исходный выбор не теряется; отдельное долговечное хранение папочного намерения между перезапусками в этот этап не добавлялось.

Сетевой/неопределённый ответ PUT проверяется через GET: если target уже текущий, подтверждается успех без нового PUT. Иначе внешнее изменение требует решения пользователя; при недоступном GET показывается неподтверждённое состояние с сохранённым выбором. 404/422/ошибки авторизации не создают новую встречу. Это CAS текущего набора, а не exactly-once квитанция/версия истории размещений; A→B→A не различается.

## Защита текста и перехода к шаблонам

Подтверждённая причина отдельного риска: прежний `SummaryEditor.setFolders` присваивал весь ответ summary, оставляя в редакторе старые title/content и saved snapshots. Ответ PUT мог уже содержать новую внешнюю редакцию; следующий PATCH со старым текстом и новой version молча перезаписал бы её.

Теперь `MeetingSummary.withFolderIds` и `SummaryEditor.setFolders` принимают **только связи**, сохраняя исходную согласованную пару content/version, title, navigation, template snapshot и локальные правки. Внешняя правка v2 → folder PUT → локальная правка старого документа v1 отправляет content CAS v1 и получает 409; серверный текст и локальный ввод остаются сохранены.

Дополнительно закрыта подтверждённая смежная граница: старый видимый original v1 мог попасть в новый выбор, созданный сервером уже с summary_version v2. `SelectionController` сверяет baseline original с opening version **до генерации и нового accept**. При несовпадении действия блокируются с объяснением; baseline/edits не повышаются и не стираются. Восстановление уже замороженного accept/cancel продолжает точный прежний запрос, а не создаёт новое намерение.

Локальная блокировка сравнения не считается закрытой серверной сессией: явная отмена отправляет DELETE и удаляет checkpoint лишь после подтверждения. При потерянном ответе повторяется тот же session ID; после подтверждения повторное расписание отмены прекращается. Реальные expired/cancelled состояния сохраняют прежнюю семантику.
