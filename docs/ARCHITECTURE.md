# ARCHITECTURE.md

# Архитектура тестовой версии

## 1. Общая схема

```text
Flutter mobile app
        |
        | HTTP
        v
FastAPI backend on developer PC
    |        |        |
    v        v        v
PostgreSQL  ASR      Local LLM
            local    local
```

Мобильное приложение общается только с backend.

Backend является точкой:
- авторизации;
- проверки прав;
- бизнес-логики;
- работы с PostgreSQL;
- вызова ASR;
- вызова LLM;
- шаринга;
- управления статусами обработки.

## 2. Технологии первой версии

### Mobile
- Flutter.
- Android — основной первый target.
- iOS поддерживается архитектурно, но можно не собирать на самом первом этапе.

### Backend
- Python.
- FastAPI.
- SQLAlchemy.
- Alembic для миграций.
- Pydantic для схем.
- Uvicorn для локального запуска.

### Database
- PostgreSQL.

### ASR
- Локальная модель.
- Предпочтительно GigaAM, если она нормально работает на имеющемся ПК.
- ASR должен быть скрыт за адаптером, чтобы позже заменить локальную модель на корпоративный API.

### LLM
- Локальная модель.
- Способ запуска не фиксируется жёстко: Ollama / llama.cpp / OpenAI-compatible local endpoint.
- LLM должна быть скрыта за адаптером.
- Позже адаптер можно переключить на LiteLLM/Qwen корпоративного ML-кластера.

## 3. Принцип заменяемых интеграций

Не писать бизнес-логику напрямую под конкретную модель.

Предпочтительная идея:

```text
services/
  asr/
    base.py
    local_gigaam.py
    remote_asr.py

  llm/
    base.py
    local_llm.py
    litellm_qwen.py
```

Бизнес-логика должна зависеть от интерфейса ASRService / LLMService, а не от конкретной реализации.

## 4. Основной поток записи встречи

1. Flutter записывает аудио.
2. Flutter отправляет файл в backend.
3. Backend создаёт запись обработки.
4. Backend запускает ASR.
5. Полученный транскрипт сохраняется в PostgreSQL.
6. Если включён ручной просмотр, статус становится transcript_ready и backend ждёт подтверждения.
7. После подтверждения либо сразу backend вызывает LLM.
8. LLM получает транскрипт, выбранный шаблон, настройки детализации и при необходимости список папок пользователя.
9. LLM возвращает summary и, при необходимости, предлагаемое название/папки.
10. Backend сохраняет персональный summary.
11. Flutter получает статус ready и загружает результат.

## 5. Асинхронные операции

ASR и LLM могут выполняться долго.

Не проектировать мобильный клиент так, будто один HTTP-запрос должен висеть до конца обработки.

На раннем локальном прототипе допустимо:
- FastAPI BackgroundTasks;
- простой asyncio task;
- polling статуса с клиента.

При усложнении:
- отдельный worker;
- очередь задач.

Не внедрять Redis/Celery до реальной необходимости.

## 6. Локальная сеть

Для тестирования на физическом телефоне:
- ПК и телефон находятся в одной сети;
- backend слушает сетевой интерфейс;
- приложение обращается к IP ПК.

Не хардкодить адрес backend в бизнес-логике мобильного приложения. Использовать конфигурацию окружения.

## 7. Безопасность тестовой версии

- пароль не хранить в открытом виде;
- использовать password hash;
- Flutter не знает пароль PostgreSQL;
- Flutter не подключается к PostgreSQL напрямую;
- секреты backend хранить в environment variables;
- не коммитить `.env`;
- права на summary/transcript проверяются на backend.

Для локальной разработки HTTP допустим внутри доверенной LAN. Production должен использовать HTTPS.

## 8. Хранение аудио

Аудио — временный объект.

Допустимый поток:
1. backend принимает файл;
2. кладёт во временное место;
3. ASR читает файл;
4. после успешной транскрибации временный файл удаляется.

При ошибке должна быть предусмотрена уборка старых временных файлов.

## 9. Транскрипты

Транскрипт является общей исходной сущностью.

Он создаётся один раз, хранится в PostgreSQL, может быть доступен нескольким пользователям через бизнес-правила и используется для создания разных персональных summary.

## 10. Summary

Summary персонален.

Он содержит:
- user_id;
- transcript_id;
- title;
- content;
- created_at.

В MVP для user_id + transcript_id должен существовать максимум один актуальный summary.

## 11. Папки

Папки принадлежат пользователю, поддерживают вложенность, summary может находиться в нескольких папках.

Для этого нужна отдельная many-to-many таблица.

По уточнению владельца проекта доступно только удаление with_contents с confirm=true: удаляется дерево, summary в других папках сохраняются. Перенос в корень не реализуется, API требует хотя бы одну папку. Мутации дерева, связей и сохранение worker сериализуются короткой PostgreSQL advisory-блокировкой на пользователя. Активная генерация в удаляемой папке даёт 409. При вызове LLM транзакции и эти блокировки не удерживаются.

После удаления summary очищается неиспользуемый transcript, если нет других summary, активной генерации или внешних FK-зависимостей. Sharing/ACL при реализации обязаны использовать FK к transcripts; текущая защитная проверка сохраняет любые такие ссылки. Не реализуется безусловное каскадное удаление общего источника.

## 12. Шаринг

Шаринг не копирует transcript.

Создаётся share request:
- from_user_id;
- to_user_id;
- transcript_id;
- status.

После accepted получателю разрешается создать свой summary из этого transcript.

## 13. Видеоконференции

MVP:
- ручная загрузка аудио;
- ручная загрузка/вставка транскрипта.

Будущее:
- коннекторы к MTS Link;
- коннекторы к IVA;
- получение готовых транскриптов пользователя через API.

Поток внешней авторизации и фильтрации конференций конкретного пользователя пока считается открытым вопросом и не должен блокировать MVP.

## 14. Production-переход

Тестовая версия должна быть спроектирована так, чтобы позднее заменить:

```text
Local PostgreSQL -> corporate PostgreSQL
Local ASR        -> corporate ASR API
Local LLM        -> LiteLLM / Qwen
PC backend       -> corporate server/container
```

Flutter при этом продолжает обращаться к тому же логическому backend API.
